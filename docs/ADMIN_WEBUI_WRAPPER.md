# Administrative WebUI synthetic wrapper

Issue #5 Phase A follow-up, stacked on the bounded-controller core. Implemented, tested in isolation and temporarily tested through live WebUI, then removed. **Not accepted for permanent deployment:** native calls and final answers remain inconsistent. No provider connection, credential handling, real resource integration, external write, new package, or new service is included. See `ADMIN_WEBUI_LIVE_RESULTS.md`.

The subsequent answer-reliability update adds sanitized terminal rejection codes and an explicitly selected `fixed_read` mode, while preserving native mode as the default. Fixed reads use a finite host-owned plan and render validated data without model calls; unsupported requests are rejected rather than partially answered. See `ADMIN_ANSWER_RELIABILITY.md` for the narrow contract, 74 current tests and direct diagnostic observations. This mode is not installed or accepted through the live chat route.

## Integration

`tools/admin_webui_pipe.py` supplies an in-process `Pipe` for a separate temporary model ID, `administrative_bounded_test`. It does not change the existing `administrative-assistant` preset or the researcher. `tools/build_admin_pipe.py` concatenates the reviewed controller and wrapper into one self-contained Python import file:

```
python tools/build_admin_pipe.py <private-scratch-output.py>
```

The inspected WebUI 0.11.4 function loader accepts this bundle as a Pipe. The loader registers its module before execution, allowing the controller's dataclasses to load. Function IDs require underscores rather than hyphens. The installed chat path supplies authenticated user information, original `request.state.metadata`, and a later per-model metadata copy. The wrapper checks that these agree on the user and temporary test model and requires a workflow identity. Client `body.metadata` cannot substitute for missing host context. This relies on WebUI's authenticated route and model access checks; the Pipe is not a Python sandbox or a separate OS security boundary.

Configure the temporary model override with memory, built-in tools, file/vision, web search, image generation, code interpreter and terminal capabilities disabled before sending test prompts. The wrapper refuses files and externally attached tools/servers. WebUI sends `memory: true` even for a memory-disabled model; the installed memory utility checks the trusted model capability before reading memories. The wrapper tolerates this inert flag only when both host model metadata copies explicitly deny memory. Active/missing-capability memory requests and other enabled features are rejected. No global memory or account preferences are changed.

The wrapper uses the existing asynchronous HTTP library and inspected loopback OVMS port, with a fixed GPT-OSS model and Native function-call request. It does not forward cookies, API keys, arbitrary URLs, user generation settings, environment proxies, or attachment tools. Redirects are disabled, response bytes are bounded, and the controller cancels cooperative HTTP operations on timeout. Preserved per-request sampling is temperature 0.1, top-p 0.9 and maximum output 4096; shared OVMS settings are untouched. It requests `tool_choice: required` before the first tool result and `auto` thereafter. This request does not guarantee that the live backend returns a parsed call; observed zero-action replies still fail verification. No malformed call names or final response formats are silently repaired.

Only synthetic Alder/Birch project lookup and read operations exist. They use the existing Phase A records and controlled error/injection scenarios. Exactly one synthetic project must be named. Fault scenarios are bound by the host to the request so the model cannot turn a denied/failing test into success by switching scenarios. Verification requires exact canonical project facts and an actual read receipt. This intentionally narrow verifier is not a general email/calendar/Drive verifier or a replacement for the current planning/drafting assistant.

## Workflow state and UI behavior

Before any model call, an atomic SQLite claim records only a digest of user/workflow identity in a dedicated test ledger under WebUI's data directory. The originating user message is preferred, so a regenerated assistant response cannot reset its claim; agreement with original server metadata is checked. Completed, stopped and cancelled IDs remain claimed across reloads. Concurrent duplicates cannot receive fresh budgets. The ledger refuses new workflows at 256 claims rather than evicting earlier entries, and storage failures deny execution. No prompts, provider contents, results or raw user identities are stored. Digests are not an anonymity guarantee. New user message IDs represent new workflows, not semantic idempotency. Legacy/isolated requests lacking the originating ID fall back to the assistant message ID; production integration must require a stable origin identity rather than relying on that fallback across regenerated response IDs. Edited requests retaining an already-claimed origin are refused; submit a genuinely new message to start new work.

Early failures return a visible stop code. Started workflows emit bounded status notifications with action/round counts and return only verified answers with source/receipt labels, or explicit stopped outcomes. Cancellation emits a finished cancelled status, propagates and retains the claim. Live Stop and subsequent regeneration were verified. This establishes cancellation reaching the Pipe, not immediate GPU work termination. Title/background tasks execute no tools. There is no automatic fallback that releases unverified model prose.

## Verified evidence and limitations

- At the original live-test revision, 65 offline synthetic tests passed under the installed WebUI Python 3.11 runtime: 26 controller, 24 wrapper and 15 existing fixture tests. Those regressions cover per-model context enrichment, explicit memory denial, cancellation status and origin-based regeneration protection. The deadline regression blocks a later round deterministically rather than relying on several short sleeps under workstation load. The subsequent reliability revision has 74 passing tests, as detailed in `ADMIN_ANSWER_RELIABILITY.md`.
- The installed loader accepts the bundle in isolated scratch storage. Temporary live import, exact trusted context, native transport, controlled loop stops, cancellation and replay rejection were exercised. WebUI formats saved Python; AST comparison verified equivalence to the reviewed bundle.
- A consistent private backup and protected hashes were refreshed before live edits. The temporary Function and model override were removed and its dedicated ledger quarantined locally. Final model/function/tool/knowledge/access-grant/global-config comparisons match the fresh baseline. No private records, logs, paths, screenshots or backup contents are published to GitHub.
- The earlier service-availability blocker was resolved by the owner opening the existing HFE Chat shortcut. No launcher, startup method, shared serving settings or research development changed.
- **Reliable live task completion is NOT established.** A verified read occurred during testing, but final-contract cases frequently stopped on invalid terminal responses or missing/malformed native calls. Some requested fault scenarios were not reached. Offline validation does not turn these into live passes. No production readiness or completion of provider phases is claimed.
